# Tech notes: building it (10,000 units, physics and shaders)

How to build the game. The game-design skill reads this for questions about simulation, performance, pathfinding, AI, physics or shaders; edit it freely, and decisions in `claude/game-brief.md` win if they disagree. The game targets PCs with mouse and keyboard, from integrated graphics at 20 fps (the floor) up to dedicated GPUs (brief, 2026-10-11). The engine is Unity (brief, 2026-10-11), but the simulation is an engine-free C# library, so the patterns here stay engine-agnostic; section 9 gives the Unity specifics, and `claude/implementation-plan.md` covers the repository, tooling and milestones.

## 1. Budget mindset

The floor is integrated graphics at 20 fps (brief, 2026-10-11): a 2020-or-later laptop with Intel Iris Xe or AMD Radeon 680M-class graphics, a 4-core, 8-thread CPU and 8 GB of memory shared with the GPU. A mid-range dedicated GPU at 60 fps is the recommended spec. Players are on Windows only at launch (brief, 2026-10-11), with DirectX 12 by default and DirectX 11 as a fallback. Compute shaders, indirect instancing and grid simulations still work on the floor, but the GPU has a fraction of a dedicated card's throughput and shares memory bandwidth with the CPU, so the lowest preset relies on a lower internal resolution with upscaling, dots and impostors for distant soldiers, a cap on full-detail soldiers and thinner effects (section 7).

Graphics settings should scale presentation only: mesh detail, shadow quality, VFX density, how finely the shader renders water and mud. Gameplay fields, unit counts and simulation rates must be identical on every setting, otherwise a low-end player would face a different battle. Every warning the player relies on (strain cracks, rising-water tint, fire fronts, landing spreads, the no-cast ring) must read on the lowest preset, so readability is never a high-end feature.

The timeline raises the bar further: the simulation must run many times faster than real time (roughly 10 to 20 times) on background threads so the player can see minutes into the future within moments of an edit. Budget the simulation tick, not just the frame (section 10). On the floor CPU, aim for about 8 times real time: the preview fills more slowly there, but the battle is identical.

At 10,000 units, anything done per unit per frame must be tiny. Push decisions up to groups, push spatial questions into grids, push visuals onto the GPU. Before recommending a mechanic, ask what it costs per unit, per frame. If a mechanic requires each soldier to reason individually (individual line-of-sight checks, individual path searches, individual rigid bodies), redesign it or run it on regiments or at a lower update rate.

Performance comes before visual flourish (brief, 2026-10-09): when a look costs per-soldier physics or per-soldier history, find a cheaper way to show it or drop it, as was done with wobble.

## 2. Units as data

Store units as tightly packed arrays of plain data (position, velocity, type, health, morale, regiment id) processed in batches: an entity-component-system or data-oriented layout. Update in parallel jobs. Avoid one game object per soldier.

Spatial hashing (a uniform grid of buckets) answers "who is near me" for separation, melee contact and crowd pressure cheaply.

## 3. Movement: flow fields, not per-unit paths

Compute one flow field per destination (or per regiment goal) over a navigation grid: every cell stores the direction toward the goal. Thousands of units then just sample the cell they stand in. Recompute when terrain changes (a tree falls, a ford floods), ideally incrementally or for affected tiles only. Terrain shaping (phase 2 of the campaign, the terrain layer of PvP) happens before the battle, so the battle itself never rebuilds for those pieces; but every terrain edit during planning rebuilds the navigation and cost grids before the preview can re-simulate, so make that rebuild incremental (affected tiles only) and fast. Units that shape the world during the battle do change these grids mid-battle (see Unit-made changes, below), through the same incremental path as a landed tree.

Cost fields feed the flow field: mud, water depth, slope, debris and congestion raise the cost of cells, which is exactly how god powers redirect armies. Make per-type cost fields (siege cares about slope and bridges far more than infantry) or a shared field with per-type multipliers.

Bonus for design: the same computation produces the player's route preview. Run the flow field with the proposed change applied and draw the attacker's predicted path before the player commits.

Add local steering on top (separation, alignment within regiment, obstacle avoidance) so crowds look organic and congestion emerges naturally at chokepoints.

**No full traps (reachability check).** Placements may never fully enclose either army (brief, 2026-10-09). Check this on a coarse copy of the navigation grid (for example 4 to 8 m cells), treating only hard blockers as closed (walls, boulders, cliffs, deep water, dense forest, the map edge); mud, swamp, shallow water and snow are costly but open, and herds are ignored because they move. For each army and each unit-type class, run a breadth-first distance fill from its deployment zone (no more costly than a plain flood-fill) and require that it reaches the other army's zone and its own retreat edge of the map, each by a route no longer than twice the straight-line distance (a tunable multiplier). Distance only: the cost fields (mud, water depth, snow) don't count toward the cap, so slowing the army stays legal. Show the route's length against the cap while dragging (for example "1.6x of 2x", amber near the limit). Use a clearance map so wide units need wide gaps: siege needs a corridor several cells wide, infantry one cell. Run the check on every placement drag (a few milliseconds on a coarse grid), so a piece that would close the last route turns red with the reason before it is dropped, the same way a fizzling cast is flagged, and draw the remaining guaranteed route as an overlay so players can see what they cannot close. In PvP, run it again at lock-in on both seats' combined placements, since hidden pieces from each side could together close the last gap; if they do, open a gap through one of the closing pieces by a fixed rule (for example the newest piece in the deterministic placement order) and mark it on the map. Blockers created during the battle (floods, fallen trees, broken ice, drifts, unit-made works) are not checked at lock-in: they must clear on their own or be clearable by engineers, and the AI waits or reroutes rather than standing stuck.

**Placed terrain pieces.** Boulders are static obstacles stamped into the navigation grid like a landed tree. Herds are the one terrain piece that moves during the battle: a small group of animal agents (tens to a few hundred per herd, capped per map) that use the same data layout as soldiers and roam by deterministic rules (grazing waypoints plus seeded random wander). Don't rebuild flow fields as herds move; write herd occupancy into the congestion cost each tick, so regiments steer and queue around them, and push through the spatial hash. Herds read the same fields as soldiers (flee heat, avoid deep water, add load to ice, churn mud).

**Stampedes.** When heat near a herd crosses a threshold (fire or a lightning strike), the herd switches to a stampede state after a short, visible agitation delay. Each animal's heading comes from fleeing the heat (down the temperature field's gradient) plus slope and blocking terrain (deep water, steep ground, boulders); speed rises and the run lasts a set time or distance before the herd calms and scatters. Collisions with soldiers resolve against the spatial hash like crushing (section 5): soldiers in the path are launched (exaggerated, section 5), seeded damage rolls, broken formation slots, then one casualty event per hit regiment for morale shock. Herd agents are few, so this stays cheap; the preview draws the stampede's path straight from the simulation.

**Unit-made changes (brief, 2026-10-09 and 2026-10-10).** Specialist unit types can shape the world during the battle: dig, fill, burn, undermine, wreck, lay bridges and herd. Each action belongs to one unit type (there is no general kit) and is a regiment-level decision under a fixed rule, carried out as deterministic edits at set ticks, never as per-soldier work:

- A dig writes ground and bank height along a line at a set rate; a fill (fascines) raises riverbed height and firmness per bundle dropped; a sap gallery writes a line of load-limited cells, like old mine workings.
- Ignition writes a fire seed into the fuel field, after a regiment-level check that the fuel is dry, the wind blows away from the unit's own side and no soldier of either side is within 30 m.
- A wreck, a felled tree or a laid bridge is stamped into the navigation grid like a landed prop; a pontoon deck gets a load strength from the water height under it.
- Engineers (brief, 2026-10-11): a trestle grows segment by segment at a set rate, each segment stamped as a bridge segment with its own load strength, standing on the bed so water still flows under it; a repair raises a damaged segment's strength back toward its maximum at a set rate; clearing removes a stamped prop (fallen tree, debris, wreck, small boulder) after a set time, then unstamps it through the same incremental path.
- Herding writes a weak fear source the herd reads like mild heat, capped below the stampede threshold.

Rebuild the affected flow-field tiles and the distance-to-lethal field incrementally, as for a landed tree. Height and riverbed edits need no special water code: the water simulation reads the heightfield each tick, so a dug ditch fills with rain and a fascine weir backs water up on its own. Batch dig progress into a few edits per second, like drifts, and cap world-changing actions per regiment and per battle (charges such as torches, bundles or metres dug), which bounds the cost in round 5. Unit-made blockers skip the lock-in reachability check, so validate each action against the coarse reachability grid before it is applied: a dig line stops short of closing the last gap for any unit class, and every result must stay clearable. Log each edit as a cause event carrying the regiment's id (section 10), which also drives the marker on that regiment's timeline lane.

Unit-specific in design, shared in code: store each specialist's action as data on its unit type (trigger rule, edit kind, rate, charges per regiment, which seat may buy it) and run every action through one shared executor, so a new specialist costs a data entry, art, an AI rule and a preview marker, not new simulation code. Charges live on the regiment and are lost when it is wiped or routs. Specialists are a priority target for both AIs, through one extra term in the regiment-level target score (section 4).

## 4. Regiments: the unit of decision

Group soldiers into regiments of roughly 50 to 200. The AI decides at regiment level (target, formation, retreat, wait for the river to drop); individuals only execute (follow the flow field, hold formation slot, fight neighbours). Morale also works well per regiment with contagion between neighbouring regiments, which gives readable waves of panic.

This keeps strategic AI cheap and makes the army readable to the player.

**Specialists as targets (brief, 2026-10-10).** World-shaping specialists carry charges that are lost if the regiment falls, so both AIs treat them as high-value: the defender's target score weights an enemy specialist by its unspent charges, and the attacker assigns the nearest fighting regiment as its escort. Both are fixed rules at regiment level, so the choice is deterministic, and the preview can show which regiment is hunting or guarding which specialist.

**Garrisons.** Towers and walls fight only through the regiment inside them, so a garrison is regiment state, not a new kind of unit. Manning is a regiment-level decision (march out, enter, hold) that the timeline preview shows, including whether the regiment reaches the structure before the attacker. Once inside, soldiers snap to fixed slots on the structure and stop following the flow field. The structure adds a height bonus to the regiment's volleys (an extra input to the range table, section 5) and a cover modifier against incoming volleys, and smoke over it lowers the garrison's sight through the same fog density field. The structure itself has a strength, like a bridge segment, that fire, tremor and siege engines lower; when it fails, the garrison switches to falling or routs, and a casualty event goes out for morale.

## 5. Physics: where it belongs and where it doesn't

- **Rigid bodies for props, not people.** Trees, boulders, siege engines, bridge segments, debris: tens to hundreds of physics objects, because they are what the player manipulates. Their gameplay outcome (where they land, what they block or crush) must be deterministic (section 8): either a deterministic physics solution or a simplified deterministic motion, with engine physics adding visual detail only.
- **Soldiers are kinematic agents** steered by the flow field, with simple pushing (crowd pressure) via the spatial hash. No rigid bodies and no ragdolls for soldiers.
- **Exaggerated launches (brief, 2026-10-09).** Impacts from cavalry charges, stampedes, falling trees, collapses and siege stones switch soldiers into a launched state: a ballistic body in the simulation (fixed-point position, velocity and spin), launched much faster than reality and falling under reduced gravity for extra hang time. Each tick it steps along its arc and checks the terrain heightfield and water; on landing it takes damage by surface (deep water, a cliff drop or fire can kill; open ground mostly stuns for a few seconds) and leaves its formation slot. A landing knocks neighbours in the spatial hash down for a short stagger but never launches them, so there are no chain reactions and small plan edits don't snowball. Cost is a few numbers and one arc step per airborne soldier, so no cap is needed for performance. Tune launch speed per source, the gravity scale, stun time and landing damage separately, so spectacle never quietly becomes lethality. For a stable, previewable landing spread (brief, 2026-10-09): take the launch direction from the source's heading (the herd's run, the tree's fall, the charge) plus a fixed seeded spread per soldier, not from contact geometry; treat a shallow fringe of about 2 m along deep water as stun-only; and keep launched and stunned soldiers in their regiment's outline for the range rule until they regroup or die.
- **Lethal cells, pushes and causes of death (brief, 2026-10-09 and 2026-10-11).** Soldiers and herds never walk into lethal cells: deep or fast water above the swept threshold, cliff drops, burning cells and broken ice, evaluated from the fields each tick (so ice, bridges and fords are entered while safe). Regiment AI never reads warning stages (load-to-strength ratios, rising water below the threshold); those exist for the player only, which keeps traps reliable and the AI cheap. The flow field treats lethal cells as closed, and local steering adds a push away from lethal edges, read from a distance-to-lethal field rebuilt for affected tiles when water, fire or ice change. Crowd pressure from the spatial hash is applied after steering and can exceed that push, so a soldier with enough pressure behind him is forced over; launches, knockback, rising water and failing ground ignore avoidance entirely. A soldier at a lethal edge with pressure above a threshold enters a teetering state (its own clip, and a warning the preview can highlight) before going over. Pushes are one cause of death among several (brief, 2026-10-11). Use one damage model, and log each death with its cause and source for the causality trace: combat (the regiment that struck), impact (trampled by, crushed by), a hazard that reached the soldier (burned, swept by rising water, fell with the ice) or being put into one (launched by, pushed by the crowd).
- **Continuous media as grids.** Water, mud, fire spread and gas or fog are cheapest as grid simulations: a heightfield shallow-water model (for example the "virtual pipes" approach) for rivers and floods; cellular spread for fire; advected density for fog and smoke.
- **Physics to gameplay handoff.** When a prop settles (tree lands), stamp it into the navigation and cost grids so the flow field updates. That stamp is the moment the redirect happens.

### Casualties from physics (powers can kill through consequences)

Hundreds of soldiers can die in one event, so resolve deaths as data, and keep the spectacle in the simulated arcs and baked animations rather than in engine physics.

- **Water.** Each soldier samples water depth and flow speed from the field it stands in. Above a depth or speed threshold (lower for heavy armour, cavalry and siege crews), it loses footing and becomes "swept": it moves with the flow, its drowning timer runs, and it can reach a bank and survive. All of this is a few numbers per soldier, no rigid bodies.
- **Load-bearing structures.** Bridges, ice, dams and undermined ground carry a load value: the sum of the mass of units on each segment (from the spatial hash) plus siege engines. Each segment has a strength that powers can lower (rot, flood scour, tremor, and for ice, melting). When load exceeds strength (a deterministic check on a set tick), the segment fails and falls, with the visible collapse free to use engine physics; soldiers on it are launched (above) and then fall into the water as swept, or die. Make the warning (creaking, sagging, cracks drawn by the shader as load nears strength) read from the same numbers.
- **Ice specifically.** Ice has no authored segments, so check load per small patch of cells (for example 4 by 4 cells), with strength taken from the ice thickness field. A broken patch turns back into open water at once, which raises the load on neighbouring patches as soldiers crowd away from the hole, so breaks can spread through a dense column but stop at a thin file. Soldiers on a broken patch switch straight to the swept state, with a cold-water drowning timer.
- **Fire (brief, 2026-10-11).** Soldiers never walk into burning cells, but a fire front can reach them. A soldier whose cell ignites, or who is launched or pushed into fire, enters a burning state with a short timer (like swept): it runs down the temperature gradient and dies if the timer ends before it reaches a cell below the burn threshold. Regiment AI orders an evacuation away from an approaching front by a fixed rule, still avoiding lethal cells. Cap the front's spread on open ground below infantry running speed (a tunable value per fuel type that wind and dry fuel push toward), so fire kills those it traps against water, cliffs, crowds or other fire rather than everyone it touches. The fuel and temperature fields already hold everything this needs; the burning state is a few numbers per soldier.
- **Crushing and burial.** Landslides, avalanches, falling trees, rolling boulders and stampeding herds resolve against the spatial hash: soldiers inside the swept volume take damage or die, and those at the edge are launched (above). Trampling and crushing damage is tuned separately from launch distance (brief, 2026-10-11).
- **Rolling boulders (brief, 2026-10-11).** A tremor or landslide can release placed boulders on a slope. Each becomes a rolling body on the heightfield, deterministic like a launched soldier: it follows the fall line, slows in mud, trees and water, stops against obstacles, and crushes or launches the soldiers it meets through the spatial hash; where it stops, it is stamped into the navigation grid like a landed tree. Rumbling and dust come first as the warning, and the preview draws its path. Keep them few per map, so the cost stays a handful of bodies.
- **Presentation at scale.** No runtime ragdolls (brief, 2026-10-09). Launched soldiers tumble along their simulated arc with a baked spin clip and land with a baked crumple. Each death plays a cartoon gag chosen by its recorded cause (brief, 2026-10-11), from a data table that maps cause to a baked clip, shader parameters (flatten, char, sink) and optional instanced props: drowned soldiers wave and sink while their gear floats off, the crushed go pancake-flat, the burned turn soot-black and crumble to ash, and so on (gag list: `claude/unit-spec.md`). The gag is driven by the death event (cause, tick, position, heading, seed), so the preview, the live battle and replays show the same one. Props are visual only: floating gear follows the water-flow field and ash follows the wind field, read from the field snapshots; cap how many show at once and thin them on the Low preset. Bodies never stay on the field (playful tone, no gore; brief, 2026-10-09): after a short beat they sink, float away or fade, so they never feed back into pathing and never pile up where the simulation has no obstacle.
- **Morale shock.** Emit a casualty event (position, count) that nearby regiments read for panic, so the morale system never has to inspect individual deaths. Mass launches emit one too, so a charge that scatters a block shakes its neighbours even when few die.

### Arrows and wind

Wind slows arrows shot into it and shortens their range, and carries downwind shots further. Resolve this per regiment volley, never per arrow:

- At each volley, sample the wind field along the shot (for example at the shooter, midpoint and target cells) and take the part of the wind along the shot direction.
- Look up maximum range, flight time and impact speed from a small fixed-point table per projectile type (light arrows, crossbow bolts, siege stones), so heavier projectiles feel the wind less.
- Height adds range: the height difference between shooter and target (a ridge, or a tower's platform for a garrison) is one more input to the same table, and a garrison's cover lowers the hits it takes from incoming volleys.
- Hits and damage come from that table plus seeded random numbers, so volleys are deterministic.
- The arrows the player sees are GPU particles following the same computed arc; any extra sideways drift is visual only.
- Draw each ranged regiment's reach as a range shape stretched downwind, computed from the same table, so the preview matches what happens.

## 6. Fields: one texture, three jobs

The strongest pattern for a shader-heavy, physics-driven game: keep each gameplay field (water height, wetness, mud, temperature, fuel, fog density, ice, snow depth, wind) in a low-resolution 2D grid, roughly 1 to 2 metres per cell, and use it three ways:

1. **Simulation** updates it (deterministically on the CPU; see below).
2. **Rendering** samples it: terrain shader darkens wet soil and blends mud, water shader reads height and flow, foliage shader burns or freezes.
3. **Gameplay** reads it: unit speed, cavalry charge, bowstring and arrow range (wind), ice strength and pathing cost all sample the same cells.

One source of truth means what the player sees is exactly what the units feel, which matters a lot for readability.

**Field interactions are the counter system.** Each tick, every cell updates its fields from the others in a fixed order (fixed order keeps it deterministic): fire spread scales down with wetness; heat evaporates water and dries mud; wind (a vector field, so opposing winds sum and cancel) carries rain, fog, smoke and fire spread; temperature below freezing converts water height into ice thickness, and heat (from fire burning nearby or a heat power) melts it back into water. Keep heat and cold as one temperature field, so fire and cold snaps push the same number in opposite directions. Ice strength follows its thickness, so melting lowers the load an ice patch can carry (section 5). Keep the interaction strengths in a data table designers can tune, rather than in code. The shaders read the same cells to show each interaction: steam where fire meets wet ground, frost creeping across water, cracks spreading as load nears what the ice holds, smoke bending with the wind.

**Cast wind.** A wind power writes a plume into the wind field: full strength over its cast area, then fading with distance downwind up to a set reach, spreading slightly sideways. Compute it analytically (a fixed-point falloff per cell, rebuilt only when a wind cast starts or ends) rather than as a fluid simulation, so it is cheap, stable and predictable for the preview. Plumes add as vectors, so opposing winds cancel. Ridges and forest cut the plume behind them through a shelter mask derived from terrain height and tree cover, which is also what shelters archers on the lee side. The range rule only checks the cast area; the plume beyond it is a consequence, like flowing water.

**Snow.** Snow depth is one more field, initialised from the level's climate (starting depth per cell; zero on maps without snow). Its rules join the fixed update order: precipitation over cells below freezing adds snow depth instead of wetness; heat melts snow into water height at a fixed ratio, and that meltwater then flows like any other water (a snowmelt surge needs no special code); snow above a set depth blocks fire spread in its cell; wind above a threshold moves loose snow downwind and drops it where the wind weakens, using the same shelter mask (behind hedges, walls and forest edges, into hollows and channels). Snow depth raises movement cost per unit type (cavalry and siege most), and regiments passing through pack it down, lowering the cost for those behind (trail-breaking). Drifts change the cost field during the battle, so update the affected flow-field tiles incrementally, like a landed tree; throttle drift updates to a few times per second so this stays cheap. Avalanches reuse the load check: per slope patch, snow load against a strength set by slope angle; added snow, heat, a tremor or a thunderclap event in range tips it, and the release moves snow mass downhill along the slope as a deterministic slide that resolves burial like a landslide (section 5). The shader reads snow depth for drifts, footprints and the packed trail; ice under snow stays visible in the planning overlay.

Because both the puzzle campaign and PvP need a deterministic simulation (section 8), run the gameplay fields on the CPU at low resolution (multithreaded, a few hundred thousand cells is fine) and upload them to the GPU each tick. The shaders add the high-detail look procedurally on top of that data. Avoid GPU simulation feeding back into gameplay: results can differ between graphics cards and would desync PvP matches.

## 7. Rendering 10,000 soldiers

Look and motion (TABS-level detail with the game's own look, exaggerated physics, no wobble, the level-of-detail ladder) are specified in `claude/unit-spec.md`.

- GPU instancing: draw thousands of soldiers per call, with per-instance data (team colour, damage, wetness, mud on legs) in buffers.
- Vertex animation textures: bake skeletal animations into textures so animation runs in the vertex shader, with no CPU skinning. The clip is chosen from simulation state and the ground fields (mud, ice, snow, water depth), and launched soldiers add a rotation from their simulated spin; no per-soldier spring or wobble.
- Level of detail by distance: full mesh near the camera, simplified mesh further away, flat impostors or even shaded particle dots at strategic zoom.
- GPU culling (frustum and occlusion) for the instances.
- Shader-driven state on soldiers is cheap and readable: wet sheen, mud creeping up legs, burning, frost, panic tint at strategic zoom.
- **Quality presets (brief, 2026-10-11).** The lowest preset targets 20 fps on integrated graphics: render at a lower internal resolution and upscale (Unity's spatial-temporal upscaler or similar), cap full-detail soldiers at around a hundred near the camera, switch to far meshes, impostors and dots sooner, render field detail (water, mud, snow) at reduced resolution, use cheap shadows and thin effects. Higher presets add detail, never information: every preset shows the same warnings, overlays and units.

## 8. Determinism (required: puzzle campaign and PvP)

Both modes need it. Campaign puzzles must give the same result for the same actions. PvP is an auto-battler: each round, only the two players' placements are exchanged, and every machine simulates the identical battle from them (a server can run the same simulation to verify results). Retrofitting determinism is very expensive, so build it in from the first prototype.

What it means in practice:

- **Fixed simulation tick** (for example 20 to 30 ticks per second) separate from the render frame rate; rendering interpolates between ticks.
- **Deterministic gameplay code.** Same inputs in the same order give bit-identical results on every machine. Floating-point results can differ across compilers, CPUs and instruction sets, so either use fixed-point maths for gameplay state or tightly control compiler settings and avoid platform-specific maths functions. Seeded random numbers only, owned by the simulation.
- **Gameplay fields on the deterministic side.** Water, wetness, fire and load are authoritative on the CPU (or a deterministic simulation); the GPU renders them with extra visual detail but never feeds results back into gameplay. This settles the readback trade-off in section 6.
- **Physics split.** Most engine physics is not guaranteed to match across machines. Anything that changes gameplay (where a tree lands, when a bridge segment fails, who it falls on, where a launched soldier lands) must come from the deterministic simulation, for example a tree falling along a computed arc and stamping into the nav grid at a set tick. Engine physics can then add purely visual debris and splashes on top. Check the chosen engine's guarantees before relying on its physics for gameplay.
- **Desync detection.** Hash the simulation state every few ticks and compare between players; log the first mismatch. Essential during development.
- **Replays come free.** A replay is just the command log, which also gives the campaign "show the best solution" ghosts and makes bug reports reproducible.
- **Rewind and scrubbing.** Built on snapshots and re-simulation; see section 10.
- **Hidden placements stay hidden.** Send each player's new placements to the opponent only when both have locked in and the battle starts; during placement, the opponent's client simply doesn't have them, so cheat tools can't reveal them.
- **No latency problem.** Battles take no input, so network delay only affects the moment both players lock in.

## 9. Engine: Unity (brief, 2026-10-11)

Unity 6 with the Universal Render Pipeline (URP), starting on the current LTS release (6.3 LTS in October 2026). The split that makes it work:

- **Simulation: engine-free C#.** All gameplay lives in a plain C# library with no UnityEngine references: integer and fixed-point maths, seeded random numbers, a fixed system order. It targets .NET Standard 2.1 and C# 9, the ceiling until Unity's move to CoreCLR (Unity 7, with .NET 10 and C# 14). Unity compiles the same source as a local package through an assembly definition with no engine references; `dotnet test`, a headless command-line runner and the PvP verifier run it on plain .NET. Cross-runtime hash tests (.NET, the Mono editor, the IL2CPP player) keep the runtimes bit-identical, which also makes the CoreCLR move safe.
- **Speed.** Hot loops are static kernels over flat arrays of plain structs, so they can run on .NET threads, in Unity jobs, or under Burst if profiling asks for it; integer maths gives the same bits on all three. Parallel work writes disjoint ranges and reduces in index order.
- **No Unity physics in gameplay.** PhysX, Unity Physics and Havok may only add visual debris on top of what the simulation decided (section 8).
- **Rendering.** Soldiers drawn with indirect instanced draws (`Graphics.RenderMeshIndirect`) from GPU buffers filled from the playback track, with compute culling and LOD bins; vertex animation textures sampled in a Shader Graph custom function; gameplay fields uploaded as textures when they change, for the terrain, water, ice, snow and fire shaders; VFX Graph for splashes, dust, smoke and embers.
- **Interface.** UI Toolkit for the planning interface and timeline, the Input System for mouse and keyboard, Cinemachine for the highlight camera.
- **Content.** Maps are authored with Unity editor tools and exported to the simulation's own map format, so the simulation never reads Unity scenes. Rules data (units, powers, field interactions, projectile tables) lives in versioned JSON, and its hash is stamped on replays and checked at PvP lock-in.
- **Art.** Models and animation are made in Blender and exported to FBX by script; vertex animation textures are baked by a Unity editor tool.

Repository layout, Claude Code setup, testing and milestones: `claude/implementation-plan.md`.

## 10. Timeline and scrubbing

Powers are queued on a timeline, and the player moves through a simulated future. All of this rests on the deterministic simulation (section 8): the plan (map, armies, queued casts) fully determines the battle, so any moment can be recomputed exactly.

- **The plan is the source of truth.** Both modes use the same plan format, built in three layers: army placements, terrain edits (placed before the battle, present from the first tick) and timed casts. Store the battle as the map plus that plan. Everything shown on screen is derived from it.
- **Keyframes.** Save a full simulation snapshot every few seconds of battle time. With 10,000 units (well under a megabyte) plus the gameplay fields (a few megabytes at 1 to 2 metres per cell), one keyframe is a few megabytes; one every 5 to 10 seconds of a 15-minute battle is a few hundred megabytes before compression. The fields change slowly, so storing differences between keyframes shrinks this a lot. On the floor machine (8 GB shared with the GPU), cap the in-memory total and spill older keyframes to disk.
- **Edits re-simulate from the earliest change.** When the player adds, moves or removes a cast at time T, discard keyframes after T and re-simulate from the last keyframe before T. Start re-simulating while the player is still dragging (with a short delay) so the result is often ready on release.
- **Edit cost depends on the layer.** Army placement and terrain edits change the first tick, so they discard every keyframe and re-simulate the whole battle (terrain edits also rebuild the navigation and cost grids first, section 3); power edits re-simulate only from the cast's time. A 3-minute battle at 15 times real time takes about 12 seconds to fill in completely, so prioritise the first minute after an army or terrain edit and keep battles short.
- **The future fills in progressively.** Simulate ahead on background threads and show how far the computed future reaches on the timeline, like a video buffering bar. Prioritise computing near where the player is looking.
- **Smooth scrubbing.** Jumping to a time means loading the nearest keyframe and simulating forward to it, which can take a fraction of a second. For smooth dragging, also record a lightweight playback track (quantized unit positions and states a few times per second, plus field snapshots) and render from it, interpolating between samples. Keyframes are for resuming the simulation; the playback track is for looking.
- **Landing preview (brief, 2026-10-09).** Aggregate the recorded launch events per source into a landing spread (a small heatmap of landing cells, coloured by outcome: stunned, or killed by water, cliff or fire) and draw it as an overlay on a held key and while a placement is dragged. It comes straight from the simulated future, so it is exact, and it appears as soon as the preview has simulated past the launch.
- **Highlights and clips (brief, 2026-10-09).** A highlight picker scores cause events by size (casualties, soldiers launched, structures failed, morale shocks) and builds each highlight as cause then payoff by walking the causality trace back from the peak. Camera modes are a setting: off, end-of-battle reel (default), live cuts, picture-in-picture; slow motion is a separate toggle. Rendering any highlight reads the playback track, so no extra simulation is needed. A saved clip has two forms: a video encoded from the playback track (may run slower than real time, in the background) with the chain as a caption, and a replay file of the map id, plan, seed and simulation version (kilobytes), which re-simulates from any camera. Stamp a simulation version on every replay; a build with a different version cannot replay it, so offer the video alongside.
- **Side quests (brief, 2026-10-09).** Campaign star quests are counters over the same cause and launch events (casts used, soldiers airborne at once, splashdowns per source, defending regiments lost), evaluated on the preview's future too, so each quest ticks off live while scrubbing.
- **Launch events in the playback track.** A few samples per second can't capture a soldier's flight, so the track also records each launch (tick, start position, velocity, spin) and landing. The renderer redraws the arc analytically from that event, so flights look identical in the preview, the live battle, replays and on the opponent's screen.
- **Rendering any moment.** The renderer draws whatever state the scrub head points at: unit instances (and herds) from the playback track, and field textures (water, wetness, mud, ice, snow) uploaded from the matching snapshot, blended between neighbours.
- **Range rule against the future.** Validate each queued cast against the simulated army positions at its execution tick, and re-validate all later casts after every re-simulation. Report invalid casts to the UI with the reason.
- **Ghost of the previous plan.** Keep the previous run's playback track after an edit, so the UI can overlay where the army went last time.
- **Causality trace.** Have the simulation log cause events (cast executed, river overflowed at a cell, bridge segment failed, ice patch broke under load, avalanche released, meltwater reached a river, herd stampeded, boulder released, soldiers launched, trampled, crushed or burned, regiment swept, garrison entered or lost a tower, and a regiment's world action such as a ditch dug, bundles dropped, a fire lit or a wreck left) with links to what caused them. Clicking a result walks back the chain.
- **Unit actions on the timeline (brief, 2026-10-09).** Each regiment's world actions come from the simulation like any other cause event, so the preview draws them as markers on that regiment's lane at the tick they happen. They change whenever an edit changes where the regiment is, so re-read them after every re-simulation, the same way later casts are re-validated.
- **PvP rounds.** During placement, each player previews locally: the round simulated from the start with the opponent's earlier placements plus their own. At lock-in, the new placements are exchanged and every machine simulates the round from the start with everything. Previews never affect the shared result. Since every round re-runs a full battle, the battle length cap and the simulation speed budget matter doubly here.
